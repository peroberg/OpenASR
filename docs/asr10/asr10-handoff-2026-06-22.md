The idle/hang is around:

```asm
f87f96: move.b  $0002(A2),D0
f87f9a: move.b  $0003(A2),D1
f87f9e: cmp.b   D0,D1
f87fa0: beq     f87fc2
...
f87fc0: rte
f87fc2: adda.w  #$0016,A2

f87fca: bcs     f87f96
f87fcc: move    #$2000,SR
f87fd0: bra     f87f92
```

Interpretation:

```text
Queue record stride: 0x16
Queue base: lowmem $00c6
Queue end:  lowmem $00c8
A queue slot is pending if byte2 != byte3.
When byte2 == byte3, the dispatcher considers the slot idle/equalized.
```

Current final hang:

```text
ASR10HANG pc=f87f9a previous_pc=f87f9e opcode=122a
```

This means the machine is scanning queue slots and finding no new work.

## IACK / Vector Findings

Raw `m_maincpu->set_input_line(level, HOLD_LINE)` without CPU-space IACK uses M68000 autovectors.

M68000 autovectors:

```text
IRQ1 -> vector 0x19
IRQ2 -> vector 0x1a
IRQ3 -> vector 0x1b
IRQ4 -> vector 0x1c
IRQ5 -> vector 0x1d
IRQ6 -> vector 0x1e
IRQ7 -> vector 0x1f
```

Observed runtime vector table:

```text
0x19..0x1f -> f882da -> ERROR 139 unused vector
0x40       -> f882da -> ERROR 139 unused vector
0x21       -> f87f76 -> dispatcher-related
0x46       -> f88f3e -> FC6818/RTE candidate but causes ERROR 129
0x4e       -> f88f06 -> accepted-looking FC6818 handler
0x4f       -> f88f22 -> accepted-looking FC6818 handler
```

Vector matrix:

```text
0x21:
  avoids ERROR 139
  enters dispatcher-like code
  does not clear source properly
  not current best candidate

0x46:
  reaches real code
  causes ERROR 129 odd address
  wrong for this source

0x4e:
  handler writes FC6818=4000
  FC6814 clears naturally
  FC6816 later set by runtime 00bf1a
  final state LOADING SYSTEM / dispatcher idle

0x4f:
  handler writes FC6818=8000
  then converges with 0x4e
  final state LOADING SYSTEM / dispatcher idle
```

Current interpretation:

```text
0x4e and 0x4f are accepted-looking service vectors.
The choice between them is not the current blocker.
```

## Latest Experiment: Gated FC6816 Clear After Setter

Implemented disabled-by-default flag:

```cpp
ASR10_EXPERIMENT_FC6816_CLEAR_SERVICE_2400_AFTER_SETTER = false;
```

When enabled, it clears FC6816 `0x2400` only after:

```text
- runtime setter at/near 00bf1a has set FC6816 0x2400
- $0d06 has been set by 00bf22
- FC6814 0x2400 is already clear
- at least one later dispatcher RTE has occurred
- FC6816 still has 0x2400 set
```

Result:

```text
0x4e + clear:
  FC6816 e480 -> c080
  clear at pc=f87fc0
  rte_count=4
  final panel LOADING SYSTEM
  final hang f87f9a
  no post-clear FDC activity
  no new error

0x4f + clear:
  same result
```

Final state in both enabled runs:

```text
FC6814=000b
FC6816=c080
FC6818=0080
FC6884=703b
FC6894=703b
```

Conclusion:

```text
FC6816 0x2400 may be an in-service/EOI latch,
but clearing it is not sufficient to advance boot.
The next blocker is probably event payload / dispatcher re-arm / timer cadence / hardware completion semantics.
```

## Current Best Hypothesis

The machine is missing a real event or hardware-side state transition after the 0x2400 service sequence.

Possible missing pieces:

```text
1. Dispatcher queue re-arm:
   a slot should become pending again but does not.

2. Timer tick/timebase semantics:
   the interrupt may need to update a counter/queue payload, not just raise IRQ.

3. FC6884/FC6894 completion:
   these timer/control registers are programmed but do not produce follow-up behavior.

4. Lowmem service state:
   $0d06/$0e82 may control whether the next event is posted.

5. LINE-A / A000 semantics:
   A000 may be an OS trap/macro that expects side effects not currently modeled.

6. Panel/FDC is not yet the direct blocker:
   no post-clear FDC activity appears.
   no panel progress appears.
```

Current narrow question:

```text
After 00bf1a and $0d06 set, which queue slot, lowmem flag, timer register, or completion signal should change to make the dispatcher leave f87f9a idle?
```
