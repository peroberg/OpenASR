## 0. One-line summary

> The OS has already loaded and queued its boot-continuation work (slot0 node `14f4`, dispatch value `89a2`), but slot0 is deliberately parked in state `0202` behind a panel-display handshake: outstanding-operation counter `$03BC` must reach zero — which requires the panel to *respond* over Channel B RX — before `f89ac2` clears slot0's bit1 wake gate.

## 2. The trap table [STAT]

| Trap | Handler | Meaning | Evidence |
|------|---------|---------|----------|
| #2 | `f88066` | Pool-availability test: compares allocation count `$0b7f` against `0xBB`; returns result in carry of stacked SR | [STAT] |
| #3 | `f88078` | Allocate node from free list `$0b6c` into A5 (error `0x90`/144 if empty) | [STAT] |
| #4 | `f880a2` | Release node A5 back to free list `$0b6c`; `$0b7f--` | [STAT] |

## 3. Trap #9: bit7 is the wake/promotion gate [STAT]+[DYN]

Full handler:

```asm
f88138: ori    #$0700,SR
f8813c: move.w $12(A1),D0       ; tail
f88140: beq    f8814e           ; queue empty →
f88142:   movea.w D0,A0
f88144:   move.w A5,(A0)        ; tail->next = node
f88146:   move.w A5,$12(A1)     ; tail = node
f8814a:   moveq #7,D0
f8814c:   bra   f8816c
f8814e: moveq  #7,D0
f88150: btst   D0,$02(A1)       ; test BIT 7 of pending byte2
f88154: beq    f88164           ; bit7 clear -> queue-only path
f88156: cmpi.w #0,$0c(A1)       ; active node free?
f8815c: bne    f88164
f8815e:   move.w A5,$0c(A1)     ; DIRECT PROMOTION to active
f88162:   bra   f8816c
f88164: move.w A5,$10(A1)       ; head = node
f88168: move.w A5,$12(A1)       ; tail = node
f8816c: clr.w  (A5)
f8816e: bclr   D0,$02(A1)       ; wake via bit7 (byte2 != byte3 -> pending)
f88172: rte
```

Consequences:

- **Slot3 (`8080`)**: bit7 set → direct promotion possible; `bclr #7` → `0080` → pending. [DYN] confirmed: dispatcher selects slot3, node `14fc` (type `0006`) reaches `f8f37a`, slot3 equalizes via `f880e0`/`f88124`.
- **Slot0 (`0202`)**: bit7 already clear → node `14f4` is queued into `+10/+12` only; `bclr #7` is a no-op; `0202` stays equalized. **Trap #9 cannot wake slot0. This is by design, not a bug.**

Architectural statement: trap #9 implements the *bit7 slot protocol*. Slot0 is parked on a *different* gate: **bit1**.

## 4. `$03BC`: outstanding panel/display operation counter [STAT]

Complete access map (data-table false positives at `f867e0`, `fa52f0`, `fb0abc`, `fb90cc` excluded):

| PC | Instruction | Role |
|----|-------------|------|
| `f89a8c` | `addq.b #1,$03bc` | increment (enqueue side), adjacent to write-ptr update `move.w A0,$03b8` |
| `f89ab8` | `subq.b #1,$03bc` | decrement (completion side) |
| `f89a20` | `cmpi.b #$1e,$03bc` | flow-control threshold 30 |
| `f89a46`, `f89a60` | `cmpi.b #$0e,$03bc` | flow-control threshold 14 |
| `f89a9e` | `tst.b $03bc` / `beq` | test entry |
| V161 `img 0xeae8` (hiRAM `~ffc4e8`) | `tst.b $03bc; bne self` | **OS drain barrier (spin until 0)** |
| V161 `img 0x127a4` | `tst.b $03bc; bne self` | **second OS drain barrier** |

No immediate initializer found in ROM or V161 → counter starts at 0 via RAM clear. [STAT]

Associated ring structure: base `$0378`, write ptr `$03b8`, read ptr `$03ba`, count `$03bc`. [STAT for the pointer/counter adjacency; MODEL for exact ring semantics]

Preferred wording: **`$03BC` counts outstanding panel/display operations or protocol units** (message / packet / pending-ACK granularity). Do **not** describe it as a per-TX-byte counter; that is unproven.

The zero-crossing action:

```asm
f89ab8: subq.b #1,$03bc
f89abc: bne    f89ac8
f89abe: movea.w $00d8.w,A0
f89ac2: bclr   #1,$0002(A0)     ; wake the slot at [$00d8] via bit1
f89ac6: st     $03c5.w
```

## 5. Completion is RX-driven, not TX-driven [STAT]

Callers of the ring/completion routines:

- Boot ROM: **zero** callers.
- V161 OS: **four**, all inside the Channel B RX parser region:
    - `ffb286` → `jsr $f89aec.l`
    - `ffb32e` → `jsr $f89aec.l`
    - `ffb3e4` → `jsr $f89a9a.l`
    - `ffb424` → `jsr $f89a9a.l`

Interpretation [STAT for call sites; MODEL for protocol meaning]:

```text
TX sends a display/panel message
panel replies / acknowledges
RX parser interprets the response
completion routine decrements $03bc
```

**Practical consequence for emulation:** a panel stub that merely *receives* Channel A output is insufficient. The panel must maintain protocol state and return ACK/status/response bytes in correct order, or `$03bc` never reaches zero and slot0 bit1 is never cleared.

Related [STAT]: the early-boot display path `f89cb0` is a *polled* primitive — `move.b D2,$fffc4817.l`, fixed delay loop (`#$1f40` dbf), then read-back from `$fffc4817`. This is why "ENSONIQ ASR-10" / "LOADING SYSTEM" appear without any DUART interrupt model. The OS replaces this with the interrupt-driven ring machinery post-load.

## 6. `$00D8` and slot0 state `0202` [STAT]

Readers of `$00d8` (ROM; none in V161):

| PC | Code | Meaning |
|----|------|---------|
| `f89abe` | `movea.w $00d8.w,A0` → `bclr #1,2(A0)` | drain wake |
| `f8bc64`, `f8bc88`, `f8bcdc`, `f8bcee` | `movea.w $00d8.w,A0` → `clr.w (A0)` | slot header clears |
| `f919e6`, `f91a16` | `movea.w $00d8.w,A0` → `cmpi.w #$0202,...` | **ROM explicitly checks the parked state `0202`** |
| `f97f12` | `movea.w $00d8.w,A0` → `tst.w $0010(A0)` | slot0 queue-head test |

No writers of `$00d8` were found with the searched instruction forms in ROM or V161; initialization is likely block/loop-based and **not yet located**. [STAT for absence under searched forms; open item]

Bit1-clear inventory [STAT]:

- Exactly **one** statically coded immediate clear in ROM: `f89ac2: bclr #1,$0002(A0)`. None in V161.
- Six *dynamic* `bclr Dn,$0002(An)` sites exist in the scheduler core (`f880c8`, `f880f6`, `f8811a`, `f8816e`, `f8826a`, `f8831a`). The scheduler is wake-bit-generic; these could affect bit1 depending on runtime register contents.

Correct phrasing: **"`f89ac2` is the only verified statically-coded immediate bit1-clear path for the slot addressed by `$00D8`"** — not "the only possible bit1-clear in the system".

`0202` is treated by ROM as an explicit, named slot state (compared literally at two sites), not a residual value.

## 7. Service channel `$14C0` and trap #D [STAT]

Trap #D handler:

```asm
f881f6: ori    #$0700,SR
f881fa: clr.w  (A5)             ; node->next = 0
f881fc: tst.w  $10(A1)          ; channel active?
f88200: beq    f8821c
f88202:   addq.w #1,$0c(A1)     ; count++
f88206:   move.w $08(A1),D0     ; tail
f8820a:   bne f88212
f8820c:     move.w A5,$06(A1)   ; head = node (empty list)
f88210:     bra f88216
f88212:   movea.w D0,A0
f88214:   move.w A5,(A0)        ; tail->next = node
f88216:   move.w A5,$08(A1)     ; tail = node
f8821a:   bra f8822a
f8821c: move.w A5,$04(A1)       ; current = node
f88220: move.w #1,$10(A1)       ; active = 1
f88226: movea.l (A1),A0         ; A0 = handler pointer at +00
f88228: jsr    (A0)             ; DIRECT CALL when idle
f8822a: rte
```

Service-channel object layout: `+00` handler ptr (long), `+04` current node, `+06` queue head, `+08` queue tail, `+0c` count, `+10` active flag.

The `$14C0` instance [STAT]:

- V161 (and V350 — identical offset and content) contains `FFF884FC` at disk offset `0x3AC0`.
- Load mapping for the lowmem chunk is **RAM = image_offset − 0x2600**, proven by exact instruction match: image `0x9908` = `4eb9 fff8 d01a` = the known OS entry instruction at RAM `$007308`.
- Therefore the descriptor loads to **lowmem `$14C0`**, i.e. `long[$14c0] = FFF884FC` = the Channel A TX-arm routine. The "who consumes the pointer" question is closed: **trap #D / `f881f6` is the consumer.**
- Twelve buffer pointers (stride `0x48`, `$1050..$13b0`) immediately precede the channel object at `$14a8`. [STAT for the data; HYP that these are the TX message buffers]

Calibration [per review]: the structure semantics are statically proven. Whether the current injected `71,xx` run takes the **direct-call** branch (active=0) or the **enqueue** branch (active=1) has **not** been logged yet, and must be. [MODEL until logged]

## 8. Channel A TX engine [STAT]

TX arm:

```asm
f884fc: move.b #$04,$fffc4805.l ; CRA = enable TX A
f88504: move.w A5,$86fc.w       ; TX context
f88508: move.l #$fff8857a,$86f8.w ; TX continuation
f88510: rts
```

`f884fc` has **zero** static references in boot ROM (no jsr/bsr/data/fallthrough — the preceding code is the IRQ demux error tail). Its only known invocation route is the `$14C0` service channel via trap #D. [STAT]

TxRDY trampoline (`$00e6` target):

```asm
f88554: movea.l $86f8.w,A0
f88558: movea.w $86fc.w,A5
f8855c: jmp    (A0)
```

Completion path at `f8855e..`: `trap #4` (release), fetch next buffer from queue at **`$00dc`** via `f8822c`; if none → `move.b #$08,$fffc4805.l` (CRA = disable TX). `$00dc` is the TX buffer queue, sibling of `$00d8`/`$00da`. [STAT]

The earlier `f88554 → $86f8=00210021` crash was a diagnostic artifact from asserting TxRDY while the transmitter was not enabled and `$86f8` was uninitialized. Correct TxRDY semantics: `TxRDY = transmitter_enabled && THRA_available`. [DYN for the artifact; STAT for the mechanism]

DUART demux error tail [STAT]: unknown ISR bit → `moveq #$91` / `trap #0` = **ERROR 145 "Unknown DUART interrupt error"** — independent confirmation of the IRQ6=DUART classification.

## 9. Node dispatch values: `0006` vs `89A2` [STAT]/[MODEL]

- Slot3's injected event node `14fc` carried `+02 = 0006` and was dispatched at `f8f37a`. [DYN]
- ROM sites `f8f2e6` and `f9098e` write `#$89a2` into a fresh node's `+02` — these are the creators of the `14f4`-class node. [STAT]
- RAM `$89a2` (image `0xB0A2`) contains an OS jump block: `jmp $3a62.w / jmp $3ab2.w / jmp $3ba0.w`. [STAT]

Calibrated statement: **node dispatch value `0x89A2` leads to an OS jump block containing several boot/continuation targets.** Which entry is taken and how indexing works is not yet observed. Do not yet state "`$89a2` is the boot continuation" without this reservation. Other node `+02` immediates seen in ROM (`882e`, `880a`, `8810`, and small even values `0002..001e`) suggest mixed semantics: small values = type/table dispatch, large values = address-like dispatch. [HYP]

## 10. The consolidated main model [MODEL — strongest links STAT/DYN as marked]

```text
OS creates/queues panel display work
  -> $03bc++                                   [STAT: f89a8c]
  -> node posted to service channel $14c0
     via trap #D                               [STAT: f881f6; DYN branch not yet logged]
  -> if idle: handler F884FC arms Channel A TX [STAT]
  -> f8857a continuation transmits message     [STAT structure; DYN pending]
  -> panel responds on Channel B RX            [MODEL]
  -> IRQ6 -> f884be -> ffb22a -> $03c0 parser  [DYN]
  -> parser routes ACK/status to completion:
     ffb286/ffb32e -> f89aec
     ffb3e4/ffb424 -> f89a9a                   [STAT call sites]
  -> f89ab8: $03bc--                           [STAT]
  -> $03bc == 0:
     f89ac2 clears bit1 on slot at [$00d8]     [STAT]
  -> slot0 leaves 0202                         [MODEL]
  -> node 14f4 becomes serviceable, promoted
     via f880e0                                [STAT mechanism]
  -> dispatch value 89a2 -> OS jump block      [STAT data; dispatch not yet observed]
```

Explicitly disproven: the slot3 event path does **not** consume or wake slot0 (tested payloads `00/01/10/7f/bf` under `71,xx`). [DYN]

## 11. Remaining dynamic proof steps

1. **Trap #D branch**: log at `f881f6` entry: A1, A5, `long[A1]`, `word[A1+04/06/08/0c/10]`; then either `trap_d_direct_call target=fff884fc` or `trap_d_enqueue` with head/tail/count before/after.
2. **`$03bc++` in the natural boot**: when does `f89a8c` run, what value before/after, which message/buffer?
3. **Which RX response decrements**: RX byte sequence → exact parser branch (`ffb286/ffb32e/ffb3e4/ffb424`) → `f89a9a`/`f89aec` → `f89ab8` → `$03bc` old/new. This defines what the panel stub must answer.
4. **After bit1-clear**: slot0 state before/after `f89ac2`, dispatcher scan, `+10 -> +0c` promotion, node `14f4` activation, `f8f37a` entry, dispatch from `89a2`.
5. **TX lifecycle**: `f884fc` (CRA=04, `$86fc`, `$86f8`) → `f8857a` byte feed (does it write `FC4807`/THRA?) → `f8855e` completion → CRA=08.

A successful run closing items 1–4 upgrades the main model to a fully proven chain.

## 12. esqpanel reuse [HYP — investigate next]

MAME's `esqpanel` devices (used by VFX/SD/EPS drivers in `esq5505.cpp`, `esqkt.cpp`) implement exactly the required pattern: a serial panel that receives display bytes and transmits key/status/ACK bytes back. ASR-10's panel (per service manual: keypad/display board with its own MCU, three-line synchronous interface) is plausibly protocol-related — EPS/EPS-16 (`ESQPANEL1X22`) is the closest display format match (1×22 VFD + fixed indicator LEDs).

Treat reuse as a hypothesis: same electrical style and related parser are likely, but the ASR-10 command set and display size may differ. Compare: bytes ASR-10 sends on Channel A vs esqpanel's expected commands; esqpanel's response bytes vs the `$03c0` parser states at `ffb3ba..ffb4xx`; control bytes (`0xFC/0xFF/0xF7` etc.).

## 13. Corrections to older documentation

- Trap #4 is **free/release**, not "scheduler/event service". Re-read old logs accordingly (e.g. `FFB4E4 -> trap #3 -> build -> f87fd2 -> trap #4` = temp object released after transform, with a separate wrapper enqueued later — explains node addresses `14fc/1504/150c` as different layers).
- `$0b6c` = free-list head; `$0b7f` = allocation count (not "finalizer pointer"/"countdown").
- The dual FDC windows (`$FC4001/03` and `$FC5001/03`) plus board inventory (custom PAL `U5 "ASR-10 V1.1"` + 74HC138/139 decoders) indicate partial address decoding; SuperGLU (`U41 ES5701`) is audio-bus glue only (CPU↔ESP/OTIS, clocks) per the Buchty VHDL reconstruction and is unrelated to FDC/DUART.
- Early-boot display messages use the polled `f89cb0` path; only post-load display uses the interrupt-driven ring.
